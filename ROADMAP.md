# Development Roadmap

This document outlines the planned future features and enhancements for DiaryPipeline and its app, Notebook Feedback Studio, specifically focusing on the transition to a full-stack architecture.

## Phase 1: The Backend Pivot (Firebase Integration) - ✅ COMPLETED

Before building complex local state for editing and exporting, we implemented a backend database (Firebase). This ensures all subsequent features are built on a persistent, scalable foundation.

### Key Capabilities:
- **Persistent Active Roster**: Save selected notebooks across devices.
- **Single Source of Truth**: All manual edits, AI drafts, and workflow statuses are saved directly to the database.

## Phase 2: Data Integrity & Workflow (The "Teacher's Pen") - ✅ COMPLETED

With the database in place, we built the tools to review and refine the AI's work.

- **Manual Override**: Teachers can manually edit the AI-parsed fields directly in the UI, saving changes to the backend.
- **Timestamped Workflow Status**: Entries surface as "Draft", "Unsaved Changes", or "Feedback Ready" with `updatedAt` and `approvedAt` timestamps. The persisted wire value is still `approved` for migration stability; the teacher-facing label is now Feedback Ready. Sent feedback is tracked separately in `feedbackHistory`.
- **Bulk Readiness**: A "Mark All Ready" action saves only entries with deterministic student diary text and skips metadata-only or empty entries.
- **Smart Navigation**: A "Next Entry" button intelligently jumps to the next entry not yet marked Feedback Ready or the next student's page.
- **Feedback Action Bar**: The active entry's workflow actions live in a persistent bottom bar: `Save Draft`, `Save & Mark Ready`, and `Review & Send`.
- **Read-Through Caching**: The app parallel-fetches from OneNote and Firebase, skipping the slow AI parsing step if the data has already been saved.
- **Diary ordering and intern preferences (2026-11-17)**: saved and freshly parsed diaries use the same date ordering, accepting compact month dates, ordinal days, and full-width punctuation/week numbers. Nearby date/week inversions stay flagged without altering student text; week resets at term boundaries are preserved. All pilot authors retain Settings in either sidebar layout for personal tone, display name, closing, and drafting prompts; owner setup remains separate. Greetings and closings can also be edited in Review & Send.

## Phase 3: Batch Processing & Sync (Performance Optimization) - ✅ COMPLETED

While Read-Through Caching makes subsequent loads instant, the *first* load of a student's page still requires waiting for the AI to parse the HTML.

- **Auto-Drafting (Completed)**: The app now automatically saves AI-parsed entries as "Drafts" to Firestore immediately upon completion. This ensures that even if a teacher navigates away, the work is preserved and subsequent loads are instant.
- **The "Sync Class" Button (Completed)**: A manual batch process that iterates through all students in a class. It fetches their pages, runs the AI parsing, and saves everything to Firebase. This allows teachers to "pre-warm" the cache for an entire class.
- **Parser Mode Metadata (Completed)**: Each class now carries its own parser mode (`ai` or `label-first`) and template version metadata so structured-template classes can avoid unnecessary API calls.
- **Explicit Label-First Failure Handling (Completed)**: Deterministic parsing does not silently fall back to AI. Teachers see the raw view and can explicitly trigger AI parsing when needed.

### Next Implementation Track: Teacher-First Sync Resilience - 🔄 IN PROGRESS

The next technical priority is to make sync reliable under real classroom conditions, especially when Gemini free-tier limits are hit.

- **Deterministic Parsing Expansion** ✅ *Substantially complete (2026-05-09)*: Label parser now handles label-label mispair (empty value rows no longer misalign pairs), merged label+value cells (`[DATE]April 19`), missing single required field, and mid-semester pages where only some entry blocks are complete. Student ID recognition extended to handle IDs glued directly to names or prefixed with `At`. Remaining untouched edge cases: 8-digit ID typos and truly untitled pages (require manual OneNote correction by student).
- **DB-First Page Loading** ✅ *Completed 2026-05-08*: When a teacher opens a page, saved Firestore entries are loaded immediately and displayed without re-parsing. OneNote HTML is fetched in parallel for freshness checks and raw-view fallback, but Firestore is the primary structured review source.
- **Page Sync Metadata** ✅ *Completed 2026-05-08*: Lightweight page records (`users/{uid}/pages/{pageId}`) track freshness, cooldown state, retry timing, and last successful parse independently from entry documents.
- **Resumable Sync Queue** ✅ *Completed 2026-05-08*: Class sync saves each page as soon as parsing succeeds. When Gemini rate-limits the AI lane, the affected page is marked `rate_limited` in Firestore, sync continues with remaining pages, and rate-limited pages re-enter the queue on the next run.
- **Provider-Aware Rate Limit Handling** ✅ *Completed 2026-05-08*: Graph fetch pacing and Gemini AI pacing are handled in separate lanes. Gemini `429` responses pause the AI lane and record a cooldown window; label-first pages process regardless of AI cooldown. Graph `429` responses abort the sync and start a short-lived Graph cooldown that blocks repeated structure fetches.
- **Two-Pass Parse Quality Threshold Review** *(needs review after first legacy batch run)*: The Pass 1 quality check uses a provisional composite threshold — all three must pass: (1) at least one entry returned, (2) at least one entry has diaryText > 50 chars, (3) extracted text covers ≥ 50% of readable page text. The 50% coverage figure and the "all three must pass" strictness should be validated against real legacy data and tuned if the threshold is rejecting good Pass 1 results or passing bad ones.
- **Firestore Read Quota Management** ✅ *Completed 2026-05-10*: Three targeted optimizations significantly reduced daily Firestore read counts: (1) Firebase SDK multi-tab IndexedDB offline persistence — reads that hit the local cache do not count against server quota; (2) notebook tree localStorage cache with a 24-hour TTL so repeated dev-server restarts and startup loads do not re-fetch the full notebook structure from Graph; (3) Firestore entry document ID sanitization replacing Graph API `!` separators with `__` so 2020 legacy class entries can be written and queried without security-rule violations.
- **Sync-Queue Read Frugality + Graceful Quota Stop** ✅ *Completed 2026-06-08*: A resumed sync exhausted the free-tier daily *read* cap. The sync loop no longer reads every stored entry on a page just to stamp a transient count (reuses `PageSyncRecord.entryCount`), and gates the reclaim/requeue scans on job counters. A dedicated classifier (`services/firestoreErrors.ts`) detects the Firestore quota error before the provider-rate-limit branch, so it is never mistaken for a Gemini cooldown; on a quota hit the run stops cleanly with the queue preserved/resumable and a "resets daily" message, and never marks a page `error`. See ARCHITECTURE §31. **This lowers reads but does not raise the ceiling** — see the deferred non-capped-database item below.
- **HTML Cleaner `<object>` Unwrap** ✅ *Fixed 2026-05-10*: `cleanHTMLForAI` previously used `el.remove()` on `<object>` elements, silently discarding all child nodes. Legacy 2020 OneNote pages (free-form layout) wrap content blocks in `<object type="text/html">`, so the old code dropped virtually all diary text (217 chars from a 38,134-char page). Fix: unwrap by moving children to the parent before removing the empty wrapper. Stage-2 textContent fallback added as a last-resort safety net when primary cleaning yields <500 chars AND <2% of the original. Result: 217 chars → 9,200 chars, 1 entry → 19 entries for a full-semester legacy page.
- **Feedback UPN Resolution Fix** ✅ *Fixed 2026-05-11*: The feedback modal was resolving the student email using only `activeStudentName` (the section group name, e.g., a Japanese name). This tenant stores students in Graph with ID-based display names (`ak1234570`), so all name-matching strategies failed. Fix: the feedback modal now passes `[selectedPageTitle, activeStudentName].join(' ')` to `findStudentEmail`, matching the entry-save path that already worked. The 7-digit student ID in the page title (e.g., "1234570 - 山田陽菜") is extracted and matched against UPN substrings (`ak1234570@school.edu`). Confirmed working on current and legacy year pages. Remaining limitation: pages with mistyped student IDs (wrong digit count or transposed digits) still require manual OneNote correction by the student. See [STUDENT_IDENTITY_DESIGN.md](STUDENT_IDENTITY_DESIGN.md) for full architecture notes.
- **Proactive Roster Pre-Load** ✅ *Completed 2026-05-30*: When a class becomes active, the app now fires `ensureClassIdentityMapLoaded` in the background with `allowGraphFetch: true`. The cached identity map is warm before the teacher opens Review & Send, making recipient resolution instant for the roster-match path. Already-warm caches are skipped (no unnecessary round-trips). Falls back to on-demand Graph resolution if pre-load fails. This also reduces the double roster lookup introduced by the `findStudentEmail` resolution-source signal landed in the same session.
- **Full-Section Page Sync** ✅ *Completed 2026-05-30*: Class sync now processes every page with a non-empty title in each student section, rather than only pages whose title contains "journal", "diary", or "week". The previous filter excluded legacy year pages named by student ID, date, or the student's name. The Firestore freshness check (compare OneNote `lastModified` against stored `oneNoteLastModified`) skips already-current pages cheaply before any Graph HTML fetch or parse call, so processing all pages does not meaningfully increase sync cost for up-to-date notebooks. Log messages now include both section name and page title (`Section / Page: ...`) to make multi-page sections readable.
- **Background Backlog Parsing — B2: Firestore-persisted queue** ✅ *Completed 2026-05-30*: `handleSyncClass` now runs in two durable phases. Phase 1 (population) creates a `users/{uid}/syncJobs/{jobId}` document and writes every discoverable page as a `syncJobs/{jobId}/items/{itemId}` sub-document before any parse work starts — already-fresh pages become `skipped`, preserved rate-limited pages stay `rate_limited`. Phase 2 (processing) claims items transactionally (multi-tab safe), processes them sequentially, and marks each `done`/`error`/`rate_limited`. Stale `running` items (browser-closed mid-item) are reclaimed at Phase 2 start; retry-ready `rate_limited` items are re-queued. Job-level counts are updated with `increment()` so progress display is a single job-doc read. Jobs are only marked `done` when `counts.queued + counts.running + counts.rate_limited === 0`. On login, the app detects any `running` job and shows an explicit Resume banner — no silent auto-resume. Firestore rules and composite index ship with the service code (MEMORY pattern).
- **Background Backlog Parsing — B3/B4a: Multi-class sync and aggregate progress** ✅ *Completed 2026-05-30*: The active roster sidebar now has `Sync All Selected`, which prepares Firestore sync jobs for every selected notebook and processes them sequentially. Per-class errors are logged and the run continues to remaining classes, so one bad notebook does not abort the whole backlog. The run sums queued pages across prepared classes and passes an offset into shared processing so the progress display reads as the full selected run (for example, `47 / 312`) rather than resetting for each class.
- **Per-class sync status chips (B4b)** *(remaining)*: Add small status chips beside each selected class after its job completes, such as `done`, `partial`, `rate limited`, or `error`. This requires storing a `Map<classId, SyncJobStatus>` or richer job summary in state and rendering it in the class list rows. Useful if aggregate progress alone feels too opaque during long backlog runs.
- **Auto-Sync Default Policy *(open product question)***: Auto-sync is currently enabled by default at `daily` frequency, meaning a stale active class silently starts a sync the first time it is opened. The retry-loop bug (2026-05-30) was fixed, but the broader question remains: should auto-sync fire without an explicit user action at all? Concerns include surprising background Graph and Gemini usage during a casual browse or live demo, and unclear feedback to the teacher that a sync has started. Options: (1) change the default to `manual` and require opt-in; (2) keep daily but show a visible prompt before firing; (3) keep the current silent behaviour and document it clearly. Resolve before production deployment or any multi-user rollout.
- **Teacher-Facing Sync State**: Surface simple states like `queued`, `syncing`, `saved`, `waiting on rate limit`, and `needs retry` so the teacher always knows whether work is safe.
- **Non-Blocking Review Workflow**: Ensure a teacher can open and review pages that are already saved even while the queue continues in the background.
- **Unresolved Feedback Attribution**: Keep malformed or unattributed peer feedback blocks in the deterministic path by labeling them `Unspecified x` instead of dropping them or forcing AI fallback.
- **Future Backend Parsing Toolkit Review**: If parsing later moves into a backend or batch-processing worker, evaluate HTML/label tooling such as `lxml`, `Beautiful Soup`, `RapidFuzz`, and `dateparser` for stronger table parsing, narrow typo-tolerant label matching, and date normalization without expanding the current frontend runtime.

### Deferred Until Later

- **Firestore plan and edition (corrected 2026-10-06)**: The project is on the **Blaze** plan; the app's named database is **Firestore Enterprise edition** in **asia-southeast1**, with the free allowance applied (`freeTier: true`) and no hard cap. The earlier note here — that the database was free-tier *capped* and could not exceed quota even with billing — described the June 2026 state and no longer applies. Enterprise bills reads by data volume (read units), and it does not index fields automatically: an unindexed query scans the whole collection. See ARCHITECTURE.md §48. Cloud Run runs in asia-northeast1, so app↔database traffic crosses regions; consider co-locating if latency matters.
- **Section-pages pagination (`@odata.nextLink`)** *(latent, surfaced by Slice 4 audit 2026-06-05)*: `getSectionPages` (and the `/sections` fetch in `collectDiarySections`) issue a single un-paginated Graph call, so OneNote's default page size (~20) silently caps discovery for any section that exceeds it. The structure audit found **zero dropped pages across 2020/2025/2026**, so this is not currently biting — add nextLink-following as cheap insurance whenever a Collaboration Space section grows past the default page size (the audit's "pages dropped" stat will flag it).
- **2020 legacy discovery is fallback-dependent** *(surfaced by Slice 4 audit 2026-06-05)*: Pre-2021 notebooks name diary sections `Study Group N`, which do not match the `diary`/`journal`/`week` regex, so `collectDiarySections` discovers them only via its `return directSections` fallback. This works today but would also sweep in any non-diary section that lands directly in a legacy Collaboration Space (Welcome, Activities, stray AI pages). Revisit only if a legacy class shows spurious sections in discovery.
- **Editable Parsing Labels**: Keep label names fixed to the canonical template for now. Revisit editable/custom label mapping only after the deterministic parser and sync queue are stable.
- **Capture Pipeline (multi-mode input adapters)** *(design captured 2026-07-09 — see [PLANNING/capture-pipeline-input-modes.md](PLANNING/capture-pipeline-input-modes.md))*: Three additive input modes — typed OneNote template (current), paper-to-OneNote photo OCR (Graph supplies image bytes; Azure AI Vision / Document Intelligence does the OCR), and a student capture portal (upload → OCR → student confirmation → submit). Architecture: a capture subsystem with input adapters (`onenote-html`, `onenote-photo`, `student-portal-upload`; `power-automate-ocr` as prototype-only) that all normalize to the existing `ParsedDiaryEntry` contract, plus a future `captureSource` provenance field. Input-side twin of the Template Contract System below (shared registry: contracts declare capture routes; capture gets per-template geometry such as QR placement). Requires tenant/licensing/data-boundary review before any student image leaves OneNote. Revisit when a paper-notebook pilot is decided, Template Contract work begins, or an OCR quality spike is commissioned.
- **Template Contract System** *(future architecture track)*: Treat `templateVersion` as more than parser metadata. Each supported template should eventually define its field schema, parser adapter, validation rules, review-surface layout, export mapping, and dashboard measurement conditions. This is a larger lift than adding one more parser because the content pane must render from a template-aware contract instead of assuming the current diary field set. Keep this behind the Class Dashboard v1 and current `labeled-diary-v1` stabilization; start with a registry for existing diary templates before attempting teacher-authored templates.

## Phase 4: Analytics & Export Engine - 🔄 IN PROGRESS

The export and analysis functions will draw directly from the validated data in the backend.

When the dashboard is built, the temporary CSV/XLSX export strip at the bottom of the class selection sidebar should be replaced by a single calm "Class Dashboard" entry button in that same slot — it is the natural, always-in-context entry point since the teacher is already looking at their selected classes there. It uses existing entries, page sync records, and `feedbackHistory` only; it intentionally avoids progress scores, diagnostic language, and revision claims until target/revision evidence exists.
- **Class Patterns V1 (landed 2026-06-01)**: The dashboard now includes class-level aggregate descriptors, measurement-condition cards, entry-count distributions, participation descriptors, and a sortable/filterable evidence table. - **Group & Individual Uptake Dashboard** *(data foundation landed 2026-05-28 — `uptakeObservedAt` on `feedbackHistory` records)*: Two-level view of whether feedback is being acted on. Individual level: one student's uptake trajectory over the semester (which feedback points were marked as observed, which weren't). Group level: what fraction of the class showed uptake on a given feedback type in a given week. The cross-level question — whether the group rate predicts individual uptake in subsequent weeks — is a social-norming hypothesis not yet studied in the WCF literature and potentially a research contribution from the ACU dataset. Query shape: `(classId, sentAt window)` aggregate over `feedbackHistory.uptakeObservedAt`, backed by the `(classId ASC, sentAt DESC)` composite index committed in `firestore.indexes.json` (2026-05-28 — an earlier note that no new index was needed was wrong; the `(classId, studentUpn, sentAt)` index cannot serve a class-only query ordered by `sentAt`). Natural home alongside the AI Reliance Dashboard in the Class Dashboard view. See [FEEDBACK_ANNOTATION_DESIGN.md](./FEEDBACK_ANNOTATION_DESIGN.md) §Group & Individual Uptake Dashboard and `PLANNING/feedback-research.md` §13 question 8.
- **Longitudinal / Multi-week Feedback (Dashboard Level)**: This feature will be built into the Class Dashboard. Teachers can select a student and a date range (e.g., Weeks 1-4) to generate a synthesis of progress. This aligns with SLA research on tracking error uptake and noticing over time, allowing teachers to address recurring problems or praise long-term improvements. The `(classId, studentUpn)` compound query shape introduced in Slice 6 of the Feedback Context work is the same shape this dashboard will use — one query pattern, two surfaces. See [FEEDBACK_ANNOTATION_DESIGN.md](./FEEDBACK_ANNOTATION_DESIGN.md) §Query Scope Decision for the rationale.

Intern-sent feedback review (custom claims + collection-group read) follows. See [PLANNING/peer-intern-feedback.md](./PLANNING/peer-intern-feedback.md).
- **Feedback Contract Reconciliation (landed 2026-05-28)**: Reconciled the `teacherFeedback` field model. Fixed a confirmed data-loss bug (vocab feedback written as `vocab` but read as `vocabItems` — silently dropped from sent messages). - **Bulk Feedback Communication**: A workflow on the class dashboard for bulk compilation, review, and sending of feedback to all students via Email or Teams.
- **The "Longitudinal" Export (Entry-Centric)**: A CSV/XLSX export where each row is a single diary entry, perfect for tracking evolution over time.

- **Multi-Purpose Application Expansion** *(concept stage — see [STUDENT_IDENTITY_DESIGN.md](STUDENT_IDENTITY_DESIGN.md))*: When the app is extended beyond journal review to other assignment types, student identity resolution changes significantly. For Teams assignment submissions, Graph provides `submittedBy.user.id` directly — no title parsing needed. For new OneNote-based applications, the recommended design is to place the student ID at the container level (section named "1234570 - 山田陽菜") rather than the content level, so all pages in that section are attributed to the student without page-level inspection. The current diary notebook (Diary Groups → pages) does not follow this pattern and cannot be retrofitted. The OneNote HTML API exposes a `<meta name="author">` tag with the page creator's display name (useful for Collaboration Space attribution), but inline co-authoring paragraph-level attribution visible in the OneNote client is not exposed in the HTML API response.
- **Assignment Work Parsing** *(future product line, not dashboard v1)*: Add support for indeterminate student work beyond diary templates, using AI and/or backend Python parsers depending on task structure. This should not be squeezed into the diary parser. Treat assignments as their own submission family with explicit assignment IDs, prompt/task metadata, identity source, parser strategy, review layout, export shape, and dashboard denominators. A realistic sequence is: (1) stabilize diary dashboard v1 and evidence drill-downs, (2) introduce a template registry for the current diary templates, (3) pilot one tightly-scoped assignment type, (4) only then generalize toward flexible AI/Python parsing for open-ended submissions.

### Feedback Quality Research Backlog *(from [PLANNING/feedback-research.md](PLANNING/feedback-research.md) §12)*

Research-derived items surfaced by the 2026-05 overnight literature synthesis. Items 1, 3, and 11 from §12 are already ✅ landed (see commits 383b441 / 19fca72 / 9305af6). Remainder is here so future sessions don't re-derive from the research doc.

Converts the teacher's first read from "what did I say?" to "did they act on it?" — the actionable continuity question the research values. ~2 hours; no schema changes. - **Feedback-state model with visual indicators** *(§12 item 6 / §8)*: Surface composition state as an at-a-glance signal — drafted, sent, acknowledged, uptake visible. Builds on `acknowledgedAt` (above) and the existing `feedbackHistory` data; the schema exists, the visual layer doesn't.

**High value, higher cost — Phase 5+ dedicated slices:**
- **Comprehensive (5+) Feedback Items option** *(§12 item 9 / §2)*: A named "Comprehensive" end-stop on the Feedback Items slider, explicitly framed as a summative / grading-cycle mode rather than a silently discouraged extreme. Removes the implicit design-against stance toward comprehensive CF and makes it an intentional, contextually appropriate choice.

Forces active reflection at receipt; supported by the Eli Review uptake literature. Near-zero schema cost; change is in the email template.
- **Pre-send sandwich-shape detector** *(§12 item 15)*: Before Send, scan the assembled message for a praise→corrective→praise sequence. Deferred until the corrective-first pattern is well-established via the prompt changes already landed.
- **Feedback-pattern summation view** *(§12 item 14)*: Aggregate view of the teacher's own feedback patterns over time — sandwich-shape rate, vague-praise frequency, correction-style distribution, ability-band feedback disparity (the equalizing-effect use case from Molenaar/Sedrakyan). Different cognitive tool than the per-student history view; requires source-tracking schema additions (`sourcePerField`, `correctionStyle`, structural-sequence fields). Natural home is the AI Reliance Dashboard noted in [FEEDBACK_ANNOTATION_DESIGN.md](./FEEDBACK_ANNOTATION_DESIGN.md). See §14 of the research doc for history-view vs summation-view trade-off analysis.
